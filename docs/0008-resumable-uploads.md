# 0008 — 可续传的分片上传

状态：已实现

## 问题

单请求上传一直能用，但它有一个在真实网络上无法回避的性质：**断线即从头再来**。一个 20 GiB 的
文件在 19 GiB 处断掉，用户失去的不只是时间，还有对"能不能传上去"的信心。对于以 TB 级自建存储
为卖点的产品，这不是优化项。

## 决定

保留单请求上传，另加一组分片端点：

```
POST   /api/files/uploads                -> {id, offset, chunk_size}
PUT    /api/files/uploads/{id}           Content-Range: bytes a-b/total
POST   /api/files/uploads/{id}/complete
DELETE /api/files/uploads/{id}
```

客户端在 8 MiB 以上走分片，以下仍走单请求——小文件用分片只会多出一次建会话往返。

### 为什么不用 tus，也不用 S3 multipart

两者都是完整协议，各有一套状态机与客户端实现。这里需要的能力只有一条：顺序分片 + 断点续传。
引入 tus 意味着客户端也要正确实现它，而 S3 multipart 只适用于 S3 后端，本地磁盘布局用不上。
定制协议的最小代价是客户端要写约 40 行切片循环——已经写了，并且被浏览器端到端验证过。

### 会话在内存里，这是有意的边界

会话存活**跨连接断开**，不跨**进程重启**。持久化会话需要一张表、一次迁移、一个清理作业，以及
处理"行还在但暂存文件没了"这类不一致。而绝大多数失败是客户端掉线，不是服务端重启。把边界写
清楚，比做一个半可靠的持久化版本更诚实。

崩溃唯一能留下的东西是暂存目录里的孤儿文件，所以 `NewManager` 在启动时清理它们——只清理本包
自己能创建的文件名（`part-` 前缀），目录里其他东西一概不动。删错文件的代价远大于留一个孤儿。

## 三个具体决定

**偏移量由服务端说了算。** 分片必须从服务端当前偏移开始；不匹配时返回 409 并带上真实偏移。
客户端据此续传，而不是猜。允许任意偏移会让重试的请求与新请求交错写入，产出哈希对不上的文件。

**失败的请求不推进偏移。** 分片写入中途出错时，暂存文件会 `Truncate` 回原偏移。否则文件会留下
一个洞，而后续续传会在洞后面继续写——最后得到一个长度正确、内容错误的文件。这是最糟糕的一类
损坏，因为它能通过尺寸检查。

**两种写入路径共用同一个发布函数。** `publishFile` 负责版本保留与审计写入，单请求上传与分片
上传都调用它。有一个测试专门断言两者对同样字节产出相同的 ETag——那正是"同一条路径"的证据，
而不只是"两边都能跑通"。

## 加锁顺序

会话管理器有两把锁：管理器锁与单会话锁。规则是**永远先管理器锁、再会话锁，且从不反向**。
Finish 与 Abort 都是先拿管理器锁把会话从注册表摘掉，释放后再拿会话锁做文件操作。

最初的写法在 Finish 的冲突分支里持会话锁去拿管理器锁，而 Sweep 走的是相反顺序——那是教科书式
的死锁，且有测试（并发分片）在那个窗口上跑。现在冲突判定在管理器锁内完成（这是允许的方向），
所以"未完成"的会话根本不会离开注册表。

## 验证

| 层次 | 内容 |
|---|---|
| 会话状态机（14 个测试） | 往返、错误偏移、失败分片不推进、并发分片只有一个被接受、owner 隔离、每用户上限、过期与清理、启动清理孤儿、禁止超出声明尺寸 |
| HTTP 协议（9 个测试） | 完整往返、409 带真实偏移、未完成不得发布、Content-Range 六种畸形输入、未知会话一律 404、目标目录鉴权、超出上限、abort 后失效、**两种上传产出相同 ETag** |
| 浏览器端到端 | `demoshot -test-chunk` 拖入 20 MiB 文件，断言服务端报告的字节数与输入**完全相等** |

浏览器这一条是必要的：单元测试证明不了前端真的在切片，也证明不了切片后能拼回去。

## 顺带修掉的一个工具缺陷

`demoshot` 里的 `jsShowFiles` 还在点旧版左侧栏的 `.rail-nav button`。React 改版后这个选择器
什么都不匹配，于是拖放检查实际上在首页上拖文件——那里没有放置目标——然后报"没有新增文件"。
选择器失效不会报错，只会让后续断言测错页面。现在它点顶栏，并且点不到会直接失败。
