## 1. Verdict

**The engineering is genuinely strong; the product claims are ahead of the code; and the two are
diverging.**

This is not a hobby file browser and it is not a Nextcloud clone. It is a narrow, deliberately scoped
file service — OIDC in, PostgreSQL as the source of truth, content-addressed or filesystem-mirror
storage, WebDAV, link/email shares, and a hash-chained audit log — with an engineering discipline that
is rare in self-hosted OSS: 911 test functions, a shared conformance suite that runs against both the
in-memory and the PostgreSQL backends, ratchet tests that fail when documentation drifts, a CI that
runs `-race` against a real PostgreSQL and a moto S3 server, and a written record of its own defects
that is more honest than most vendors' release notes.

None of that is the problem. The problem is threefold. The most recent work — the file-operation
consistency layer that ADR-0013 describes at length — is **not wired into any production route**; the
WebDAV path it was meant to fix has reproducible data-loss defects that the normal test suite does not
run; and the store's headline atomicity claim fails in four independent places, in exactly the shape the
project itself named as forbidden (read, decide, then write).

| Axis | Grade | One line |
| --- | --- | --- |
| Architecture and design intent | **A−** | Coherent invariants, one authorization choke point, honest failure modes. |
| Test discipline | **A−** | 911 tests, dual-backend conformance, doc ratchets, mutation-tested guards. |
| Security model | **B+** | Two origins, hashed tokens, fail-closed audit and 404-not-403 all hold; permission model has three inconsistent route families. |
| Data-safety correctness (all write paths) | **D** | Conditional PUT and COPY can destroy bytes; a fold-colliding upload overwrites silently; four compare-then-write paths are not atomic; seven red probes sit outside CI. |
| Operations / day-2 | **C** | Excellent intent (alerts, drills, runbooks); no build version, no schema gate at boot, restore drill can drop production, backups unprovable. |
| API quality | **C+** | Functional and mostly coherent; OpenAPI drifts, listing truncates silently, no share management. |
| Web UI | **C** | Clean, accessible, prettier than most; not a team file space (Back exits the app, no share panel, read-only "shared with me"). |
| Product completeness vs. the market | **D+** | No sync client, no mobile, no LDAP/SAML/SCIM, no group spaces, no office, no full-text search, no federation. |
| Competitive distinctiveness | **B** | Verifiable audit is close to category-of-one, and the ops story is genuinely differentiated. |

**Bottom line.** Do not market this as a Nextcloud replacement yet — the README already says so, and
that sentence is the most important line in the repository. Market it as what it is: a **verifiable,
single-binary file service for regulated small teams**. Before that can be true: fix the tree-layout
write ordering and the fold-collision overwrite (two files, days not weeks), move the four
compare-then-write paths onto the atomic primitives the store already has, commit the work, and stop
claiming class-2 WebDAV and file-operation atomicity until ADR-0013 is actually on the request path.

## 3. What the product is

Three decisions define it, and they are consistent throughout the code:

1. **The database owns the metadata; the content store owns bytes.** Two storage layouts sit behind one
   interface: `blob` (content-addressed, deduplicating, cheap versions, unreadable by `ls`) and `tree`
   (filesystem mirror, `rsync`-able, versions are full copies, and — documented as a limitation —
   version *content* is not retained). The layout is chosen per deployment, never per user.
2. **Two credential systems.** Browser sessions (HMAC-signed) and App Passwords (random, stored as
   SHA-256) never mix; WebDAV refuses session cookies by design because a desktop client cannot do an
   OIDC redirect. Only human-chosen secrets (share passwords, break-glass) use Argon2id.
3. **A write and its audit record share one transaction, and the audit fails closed.** If the event
   cannot be appended, the mutation rolls back and the client gets `503 audit_unavailable`. The
   application role has `INSERT` but not `UPDATE`/`DELETE` on the audit table, so append-only is a
   PostgreSQL grant rather than a convention.

Underneath: `Deny with 404 never 403`; `authz.Cap` as an unforgeable capability bound to one node ID so
a handler that forgets to authorize has nothing to pass to the store; content-addressed blobs published
by `rename(2)` so an interrupted upload leaves an orphan rather than a row pointing at missing bytes;
and a hash-chained audit log with external daily anchors so a truncated tail is detectable.

The audit chain is real, not theater [verified: `internal/audit/audit.go`]. It uses an explicit,
hand-written canonical encoding rather than a marshalled struct precisely so that adding a field cannot
silently change historical hashes, and there is a documented, correct treatment of PostgreSQL's `inet`
prefix rendering that once made every event with an IP fail verification.

## 4. Architecture review

**What is right.**

- **One authorization choke point.** `authz.Actor` has unexported fields and `Cap` can only be produced
  by `Service.Authorize`. This is the correct Go idiom for making authorization bypass a compile-time
  problem rather than a review problem, and it is used consistently.
- **Fail-closed audit in the same transaction.** Rare and valuable. Most "audit logs" in this market are
  a log file that the app writes after the fact.
- **Two-origin content split** (`public_url` vs `usercontent_url`) with a **distinct hostname**
  requirement and an explicit opt-out that warns on every boot. Uploaded HTML/SVG therefore executes on
  an origin with no session cookie.
- **Capability-typed rollback.** The `swap` package forces a stage to declare whether it is
  `Disposable` or `Borrowed`, which is why a failed MOVE returns the user's own source instead of
  deleting it. This is a genuinely good API design decision.
- **Documentation as a test target.** `TestDocumentsCiteOnlyRealTests`,
  `TestGapTableDoesNotClaimClosedGapsAreOpen`, the requirements traceability ratchet, and the audit
  vocabulary ratchet are unusual and they have caught real drift.

**What is wrong or risky.**

- **The newest subsystem is inert.** ADR-0013's consistency machinery (`consistency.OpenLive`,
  `fence.Locker`, revision/store abstractions, staging no-replace publish, journal-backed recovery) has
  **no non-test caller** [reported, and consistent with `git ls-tree HEAD internal/` showing those
  packages are untracked]. No DAV request writes a journal row, so the startup `Recover()` call cannot
  recover a DAV swap it never recorded. The tree store's startup probe is wired for a no-replace path
  that no write uses. A comment in `move.go` cites a `reconcileOverwriteArtifacts` startup repair that
  does not exist anywhere in the tree.
- **Comments narrate review history.** A 21% comment-line ratio is defensible for this kind of code,
  but comments like "the seventh review reproduced…", "P0-R7-001", "Round 46 claimed…" are a
  development diary. They make the code harder to read for someone who was not there, and they decay
  into false statements the moment the code changes (two already have).
- **Documentation volume is now a liability.** `implementation-record.md` is 1,539 lines of round-by-round
  narrative; `functional-requirements.md` 45k characters; ADR-0001 and ADR-0013 are ~93 KB each. The
  reference material that an operator or a new maintainer needs is buried in it. The project has more
  documentation than code comments than most teams have tests — and the ratio has inverted: the docs
  claim behaviour the request path does not implement.
- **Single-writer assumptions leak.** Sessions, locks and jobs are PostgreSQL-backed (good), but
  resumable upload staging is local to one directory, and there is no cross-node resume. The README
  says this; the architecture page is slightly more optimistic than the code.

## 5. Defect register

Consolidated and de-duplicated across the subsystem reviews. Severity is about consequence, not about
how hard the fix is — most of these are small.

**The systemic finding, which matters more than any single row below.** The project's third design
principle is *"Conditional writes are decided in the same SQL statement that changes the row. Read-then-write
loses updates under concurrency."* Four independent paths do exactly what that sentence forbids:
the DAV `PUT` decides its precondition from an earlier read and then calls `UpdateFile` without the
`Expect` parameter the store already supports; `TrashCapped` compares then blind-updates; `LOCK` uses
`INSERT … NOT EXISTS`, which cannot see an uncommitted row; and the download gate charges after a
separate read. The store was built with the right primitives — `Expect`, `SELECT … FOR UPDATE SKIP
LOCKED`, a delta-based quota check — and the callers do not always use them. This is the single
highest-leverage thing to fix: it is a wiring problem, not a redesign, and it invalidates the strongest
claims the README makes.

## 6. Security model: the strongest part, with a vocabulary problem

The architecture survives adversarial reading [reported]. Two origins are enforced in the route tables
*and* by configuration validation on hostname, not just by a reverse proxy. Tokens are stored as
SHA-256 hashes with purpose-bound HMAC keys, the purpose is checked before the MAC, and comparisons are
constant-time. Audit is fail-closed on every write path that was read. `404`-not-`403` is applied
consistently, with argued exceptions (`429`, `503`).

The failures are not architectural; they are **one missing invariant**. Three route families reach the
same node — path-based (`/api/files/*`), id-based (`/api/files/thumbnail?id=`, `/api/shared/{id}/content`)
and share-token-based (`/s/{token}`) — and each implements "may this actor see this?" independently.
The result is that the same grant yields different answers on different routes (M1, M10 and H10 above).
The fix is a single shared predicate — `may_take_bytes(cap)` — rather than eleven call sites.

Two findings are worth separating because they undermine a headline claim:

- **H11**: the content-ticket route serves user bytes without an audit row. The README says "a write
  that cannot be audited does not happen" — true — but the companion expectation, that reads are
  recorded, is not universally true. Not a vulnerability; a compliance gap in the route the two-origin
  design exists to serve.
- **H5**: logging share tokens is the single most likely way a share capability leaks in practice, and
  it happens at INFO on every request.

---

## 7. WebDAV: a good class-1 server with a class-2 lock register

This is the area where the README's language is furthest from the code, and it matters most, because
WebDAV is the *only* sync story the product has.

**What works.** OPTIONS, PROPFIND (depth 0/1), GET with Range, PUT, DELETE, MKCOL, MOVE and basic COPY
behave. Auth is App-Password-only and correct. The ETag format is consistent. rclone will sync a basic
tree.

**What breaks real clients.** [reported, with the conditions reproduced by probes]

- Renames from Windows Explorer fail with `502` when the `Destination` header's host:port is not
  byte-identical to `public_url` — a normal situation behind a proxy.
- Conditional requests do not mean what RFC 7232 says (M2), and on the tree layout a rejected
  conditional **destroys the bytes** (C1).
- `supportedlock`/`lockdiscovery` are missing, LOCK on an unmapped URL returns `404` instead of creating
  an empty resource, a `Depth: 0` LOCK reports `infinity`, and tagged `If` refresh returns `412`.
- Locks are advisory in practice: COPY/MOVE/DELETE bypass them (H2), and PostgreSQL can hold two
  exclusive locks on one node (H3).
- Dead properties are write-only.
- `Content-Range` on PUT is accepted and silently truncates; chunked PUT is uncapped (H1).
- COPY ignores `Depth: 0`; collection ETag/Last-Modified never change when children change; quota live
  properties are never emitted.

**Crash behaviour.** The journal-less swap is defensible *as a documented degraded mode* only. Today a
crash between `old→backup` leaves PROPFIND `200` and GET `404`; a crash between `staged→final` leaves new
bytes under the old ETag and length. There is no startup scan and no GC for the leftovers. And because
the journal is not wired in (C5), none of the recovery code that exists can run.

**The seven red probes are the honest part.** `internal/dav/phase0_red_test.go` carries
`//go:build phase0red` and a comment stating plainly that these tests fail against the current
implementation and stay red until the owning phase lands. That is admirably honest — and it means
`go test ./...` is green while seven data-safety defects are open. The build tag should be paired with a
line in the README, not only in a source comment.

---

## 8. Data layer (metadata store)

The store is the largest subsystem — 105 files, an in-memory backend and a pgx/PostgreSQL backend behind
one contract, with a shared conformance suite that runs against both.

**The core is genuinely well built.** Business change, audit event and job enqueue commit in one
transaction; a failed audit insert rolls the whole thing back; quota is checked as a delta under a row
lock rather than by recounting; the upsert path takes `FOR UPDATE`; every value is a bind parameter and
no SQL injection was found anywhere in the subsystem; the migrations apply cleanly, twice, through the
binary's own applier. That is a better data layer than most projects this size have.

**The weakness is uniform, and it is the compare-then-write shape** described in §5: locks, the trash
cap, download charging and the DAV precondition all read, decide, and then write in a later statement,
while the comments and ADRs say the decision happens inside the writing statement. PostgreSQL's default
isolation does not rescue this.

**The second weakness is accounting on non-happy paths.** Retention expiry moves a row without moving the
bytes it was charged for, and the subsequent purge subtracts from a counter that was never credited, so a
quota leak survives the purge (H14). Foreign-key violations collapse into `ErrNotFound`, turning a
storage fault into a `404` (M18). The in-memory backend diverges from PostgreSQL on edges the shared
suite does not test (M19), which is exactly the class of bug the dual-backend suite was built to prevent
— the suite is good, but it is not yet load-bearing on the edges.

**Documentation that does not survive contact:** ADR-0004 §4 (conflicting upload must fail), the
architecture page's conditional-write and lock claims, and the cursor ADR's ordering claim. All three are
load-bearing sentences; two are false in the code and one depends on collation.

---

## 9. API and web client

The API is coherent for a system of this size: REST-ish, cursor-paginated, `FileNode`-shaped, stable
error bodies. It is not documented well enough to integrate against (M7), and the listing contract is
half-implemented on both ends (M8).

The UI is better than its feature count suggests. Contrast is measured in CI against WCAG AA across
three themes, focus-visible and reduced-motion are handled, dialogs are native `<dialog>`, and the files
view — upload with progress, drag-and-drop, grid/list, previews for images/video/audio/PDF/text —
works. It is also visibly a single-developer product: Browser Back exits the app instead of navigating;
two "Retry" buttons are inert; search exists only as a command palette; there is no share panel, no
"copy link again", no office preview, no mobile layout evidence, and nothing in the UI tells a user that
a 500-entry folder was truncated.

---

## 10. Operations

The intent is unusually operator-literate: `/healthz` and `/readyz`, 18 alert rules with a runbook,
an audit-failure policy document, a restore drill with published measurements, and a `drill`
subcommand. It is also the area where "pilot-grade" is the right description (see the ops notes for the
full list).

The five that would bite first, in order:

1. The **restore drill can drop production** (C4).
2. **No version and no schema gate** (H8) — during an incident nobody can answer "which build is this?"
   and a binary ahead of its schema serves traffic until it 500s.
3. **`/metrics` and `/readyz` on the public internet** in the reference deployment (H4).
4. **Backups that cannot be proven** (M14) — a snapshot name that is a literal string, a dump whose
   contents are unchecked, no off-host copy, no age alert.
5. **Deploys kill uploads** (M13).

Plus the migration story (M11), which is the single biggest blocker to an SRE operating this under
change: no lock, no checksum, no down path, an `ACCESS EXCLUSIVE` constraint on the largest table, and a
timeout that will abort a large backfill halfway.

### 11.2 Where newCloud actually wins

1. **Verifiable audit. Nobody in this set has it.** Nextcloud ships an editable `audit.log` file; Pydio

2. **Day-2 operating model, if it is fixed.** "One binary, one database" is a real differentiator

### 11.4 Choosing between them (for the reader)

- **You need a team file space with desktop and mobile sync, office editing and an app ecosystem, and
  you can afford €71/user/year plus the ops:** Nextcloud. Nothing here replaces it.
- **You want Nextcloud's shape without PHP, and you accept a Compose-first deployment:** OpenCloud or
  oCIS. Note the fork history and that Helm/LTS are paid.
- **You need block-level delta sync and a virtual drive on slow links:** Seafile. Budget for Pro if you
  need SSO, audit, AV or clustering.
- **You need an MFT / SFTP gateway, not a collaboration suite:** SFTPGo.
- **You need a small, auditable file service for a regulated team of 10–200, you already run PostgreSQL,
  and "prove who did what" is a requirement:** newCloud is the most interesting thing in this table —
  *after* the tree-layout write ordering and the claimed WebDAV guarantees are reconciled with the code.

## 12. What I would do next, in order

**P0 — before any external claim, ~1 week**

1. Fix the tree-layout write ordering: stage, then decide, then publish. C1/C2/C3 are one root cause.
   Add the red probes to the default suite so they cannot regress into CI's blind spot.
2. Fix the fold-colliding upload (C6): the name lookup for a write and the name lookup for a read must
   agree, and a conflict must return `ErrConflict` as ADR-0004 says.
3. Move the four compare-then-write paths onto the primitives the store already has: `UpdateFile` with
   `Expect` for conditional PUT, `SELECT … FOR UPDATE` (or a unique index) for `LOCK`, an atomic
   `UPDATE … WHERE` for `TrashCapped`, and a single statement for download charging.
4. Fix the drill's DSN guard (parse and compare; refuse if `current_database()` matches the live one).
5. Either wire ADR-0013 into the DAV routes or rewrite ADR-0013 and the README to say it is designed,
   not shipped. The current state — a 95 KB ADR, a 24 KB implementation record, and no caller — is the
   worst of the options.
6. Commit the work. 70 untracked source files is the single highest process risk in the repository.

**P1 — the "credible pilot" set, ~2–4 weeks**

7. Cap chunked bodies (`http.MaxBytesReader`), fence locks on every write path.
8. Fix the retention/purge accounting (H14) and make the trash cap actually cap (H15).
9. One shared "may take the bytes" predicate across all eleven content routes; resolve the thumbnail
   contradiction.
10. Redact `/s/*` from logs; block `/metrics` and `/readyz` at the proxy; fix the two dead alerts.
11. A build version, a schema check at boot, a migration advisory lock.
12. Real WebDAV interop: rclone, Cyberduck, Windows Explorer and Finder, published as a matrix. This is
    cheap and it is the evidence the product most needs.

**P2 — product, in value order**

13. Group-owned spaces (the only missing collaboration primitive that matters).
14. Share management in the UI, plus cursor pagination in the client.
15. A Helm chart and a measured footprint/throughput table.
16. LDAP (not SAML, not SCIM) if the target buyer is an AD shop.
17. Trash/version retention policy, legal hold, and an antivirus hook — the rest of the compliance story
    that the audit chain starts.
18. SBOM, signed releases, SECURITY.md, a CHANGELOG, and tags.

**Do not build:** a desktop sync client, CalDAV/CardDAV, federation, an app store, or AI. Each one
converts this from a focused product into a worse Nextcloud, and the sync client alone is a multi-year
commitment against two mature competitors.

## 13. Closing judgement

The most interesting thing about this repository is not its feature set; it is the *method*. A shared
conformance suite across two storage backends, documentation that fails the build when it cites a test
that does not exist, mutation-tested guards, red probes kept in the tree with a comment saying they are
red — that is a better engineering culture than most commercial file-sharing products have.

The most dangerous thing about it is the gap between that method and its output. The method produced 1,539
lines of implementation record describing 47 rounds of fixes, and it did not notice that the consistency
layer those rounds produced is not called by anything, that a rejected `If-Match` deletes a file, or that
the "decided in the same SQL statement" principle is violated in four places. The documents are the
product's biggest asset and its biggest risk: they are convincing enough that a reader stops at them.

Fix the write ordering, wire the atomic primitives, commit the work, and delete two-thirds of the prose.
What is left would be a credible, unusually trustworthy file service — small, honest, and provable. That
is a better position than "a Nextcloud replacement", which it is not.
