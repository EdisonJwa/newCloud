# 0006 — 界面重构：Atrium

状态：已选定并实施
取代：`0005-interface-design.md`（保留作历史，其结论已被本文取代）
范围：`web/`（React + TypeScript + Vite）与 `internal/webassets`

---

## 1. 前两次为什么失败

前两轮改的是**皮肤和列数**，没有改**结构隐喻**。三次尝试的共同骨架都是：

```
左侧导航栏 + 主区域列表 + 右侧详情面板
```

这正是任何一个文件管理器（Finder、Explorer、Drive、Dropbox、Nextcloud）的骨架。在这套骨架里，
无论换配色、换字体、把面板改成按需出现，用户看到的第一眼仍然是"又一个网盘"。这是一个可以用
一句话概括的失败原因，也是本文档存在的理由。

**结论：不再以"文件列表 + 面板"作为界面起点。**

---

## 2. 方向探索

三个方向在结构上彼此不兼容，不是同一骨架的不同皮肤。

### D1 — Launcher（命令优先）

界面主体是一个始终聚焦的输入框；一切功能都是它的结果集。参考 Spotlight、Raycast、Notion 的
搜索结果页。

- 优点：重度用户极快；实现简单；个性强
- 缺点：**发现性差**——不知道有什么功能的人无从下手；浏览大目录时失去空间感；
  普通用户（本产品的多数使用者）需要先学会"要输入什么"
- 评估：易用 2 / 密度 3 / 无障碍 4 / 成本 低 / 个性 5

### D2 — Stream（时间流优先）

首页是一条按时间排序的对象流（最近改动、被分享、被访问）。文件树是次入口，主要靠搜索与筛选
到达。参考 Dropbox 的 Recents、Photos 的"最近"。

- 优点：**直接表达产品主张**（可追溯性）；零学习成本；对"回来接着上次"这一最常见场景最优
- 缺点：深层目录浏览弱；重命名/移动等结构操作没有自然位置；容易滑向"仪表盘"
- 评估：易用 4 / 密度 3 / 无障碍 4 / 成本 中 / 个性 4

### D3 — Columns（空间层级优先）

每一列代表路径的一层，路径本身可见。没有面包屑，没有侧边栏。参考 Finder 的列视图、Miller
columns。

- 优点：**空间记忆**——位置即路径，比面包屑更容易记住；层级深度一眼可见；
  键盘导航天然（左右换层、上下换项）；与"列表 + 面板"完全不同
- 缺点：宽而浅的目录（500 个文件在同一层）列会显得拥挤；需要横向滚动；
  手机上是压栈式，退化为普通的逐层进入
- 评估：易用 4 / 密度 5 / 无障碍 4 / 成本 中 / 个性 5

### 评估汇总

| 方向 | 易用 | 密度 | 无障碍 | 成本 | 个性 | 结论 |
|---|---|---|---|---|---|---|
| D1 Launcher | 2 | 3 | 4 | 低 | 5 | 作为命令面板（⌘K）吸收，不作主体 |
| D2 Stream | 4 | 3 | 4 | 中 | 4 | 作为**首页**吸收 |
| D3 Columns | 4 | 5 | 4 | 中 | 5 | 作为**文件浏览**吸收 |

### 选定：D2 + D3 的组合 —— Atrium

不是折中，而是**两个不同问题用两种不同的界面回答**：

- 「我上次在做什么、什么被分享了」→ **首页（Stream）**，对象优先、时间排序
- 「我知道东西在哪，让我去拿」→ **文件（Columns）**，空间优先、层级可见

这两件事在同一个界面里争夺同一块区域，才是前几版真正的问题。分开之后，两者都不需要妥协。
D1 的 Launcher 降级为命令行面板，服务于重度用户的"我知道名字"场景。

## 3. 结构与四个决定性决定

### 3.1 没有常驻侧边栏

导航是**顶栏中的一组分区**。这是与之前所有版本最直观的差别：界面没有左侧栏，内容获得全宽。

理由：侧边栏在文件管理器里承担"位置 + 层级 + 树"三重职责。一旦层级改由列视图表达，侧边栏就
只剩"分区切换"这一件事，而为一件事付 216px 是不划算的。

### 3.2 文件页是列视图，不是"列表 + 面包屑"

```
┌──────────┬──────────┬──────────┬───────────────┐
│ 合同      │ 2026     │           │  预览          │
│ 设计稿 ●  │ Q1.pdf   │           │  名称 / 属性    │
│ 图片   ⇢2 │ Q2.pdf ● │           │  版本 / 分享    │
└──────────┴──────────┴──────────┴───────────────┘
   第 1 层     第 2 层    选中文件     详情
```

- 点击文件夹：截断其右侧所有列，追加新列
- 点击文件：最右列变为详情（预览、属性、版本、分享）
- 没有面包屑：路径就是左边的列，因为每一列的标题就是该层的名字
- 键盘：`←/→` 换列，`↑/↓` 换项，`Enter` 进入/打开，`Backspace` 退回

### 3.3 首页是真实数据，不是仪表盘

三个区域，每个都可操作，没有装饰性卡片：

1. **继续** — 最近修改的文件，带真实缩略图，点击直接进入预览
2. **你分享的** — 链接卡片，显示类型、已用次数、过期时间；可直接吊销
3. **这个空间** — 已用/配额、文件数、最近一次活动

### 3.4 预览是沉浸式的，不是带标题栏的弹窗

全幅渲染，元数据压缩成一条细带，同目录兄弟文件作为底部胶片条，`←/→` 切换。这是唯一能让人
"在文件管理器里看完一张照片"的做法。

## 4. 视觉语言

前两版用了暖纸色 + 等宽元数据，观感接近开发者工具。这一版：

- **冷中性底 + 墨色文字**，接近白纸而不是米色纸
- **单一强调色：深翡翠绿**（明 `#0B6E4F` / 暗 `#4ADE80`）。语义上对应"已存、已校验"，
  与这个产品（哈希链审计）契合；同时避开这一品类无处不在的蓝色
- **元数据全部等宽**：大小、日期、计数、路径。这一个决定同时给出精确感与列对齐
- **颜色只用于含义**：文件类型、状态、分享态。选中与焦点用墨色，不用彩色——所以危险操作
  不能只靠红色区分，它同时有图标与文字（WCAG 1.4.1）
- 近乎直角（2–4px），1px 细线分层，只有浮层有阴影
- 动效 120–160ms，仅 transform/opacity，尊重 `prefers-reduced-motion`

### 三套主题

明、暗、高对比。高对比不是反色：纯黑底、白字、每行实线边框、黄色焦点环，用边框替代表面差异。

## 5. 信息架构

```
Atrium
├── Home      最近活动、你分享的、空间用量
├── Files     列视图（核心）
│   ├── 列 = 层级
│   ├── 最右列 = 详情（预览 / 属性 / 版本 / 分享）
│   └── 拖拽上传 / ⌘K / 键盘导航
├── Shared    链接列表，可吊销
├── Activity  审计时间线，可筛选、可导出
└── Access    App Password / WebDAV
```

分享落地页 `/s/<token>` 独立于外壳，无会话。

## 6. 响应式

| 宽度 | 文件页 | 顶栏 |
|---|---|---|
| ≥ 1200 | 3–4 列并排 | 完整 |
| 760–1200 | 2 列 + 详情覆盖 | 分区文字收缩为图标 |
| < 760 | 单列压栈，返回按钮 | 分区图标 + 当前分区名 |

手机上的列视图退化为**逐层进入**：一次只显示一层，返回回到上一层。这与 Miller 列视图的语义
一致，只是把"横向展开"折叠成"纵向栈"。

## 8. 无障碍与国际化

- 列视图每列是 `role="listbox"`，`aria-activedescendant` 跟踪当前项；列本身是 `role="group"` 并带 `aria-label`
- 所有图标按钮必须有 `aria-label`
- toast 同时写入 `aria-live="polite"` 区域：只做视觉提示等于对读屏用户静默失败
- 焦点环 2px 且永不被裁切；焦点随列切换移动
- WCAG 2.2 AA：正文 ≥ 4.5:1、UI 边界 ≥ 3:1、触控目标 ≥ 24px（移动端 44px）
- 全用逻辑属性（`padding-inline`、`inset-inline-start`），`dir=rtl` 整体镜像
- i18n：键表 + `Intl.PluralRules` / `Intl.DateTimeFormat` / `Intl.NumberFormat`，不做字符串拼接
- 已内置 `en`、`zh-Hans`；语言可切换并存本地

## 9. 技术栈决定

用户指定的方向是 TypeScript + React + Vite，并允许"若现有前端已合适则保留"。

**决定：采用 React + TypeScript + Vite。**

理由不是"React 更好"，而是前端的复杂度已经到了手工 DOM 操作不合适的地步：列视图需要按路径
增量维护多个列表、每列独立加载、焦点在列间迁移、详情面板与预览共享选中态。这部分用命令式
DOM 代码写出来是 3000+ 行且难以推理——前两版的维护性问题正源于此。

代价与缓解：

| 代价 | 缓解 |
|---|---|
| 引入构建步骤 | 构建产物提交进仓库，`go build` 仍然一步产出可部署二进制 |
| npm 依赖树 | **运行时依赖为零**：产物是静态 JS/CSS，npm 只存在于开发期 |
| 前端与二进制可能不同步 | 产物内嵌进二进制；`make web` 重新生成 |

`internal/webassets` 相应改为内嵌 `web/dist`（由 Vite 直接输出到该目录，省掉复制步骤）。

### API 类型

REST 契约以 `web/src/types.ts` 手工镜像。**没有**引入 OpenAPI 代码生成：为 15 个端点引入
生成器与 schema 校验的维护成本，高于它在这里能带来的收益。如果端点数量显著增长，或出现第二个
消费者（移动端、CLI），再补 `openapi.yaml` + 生成就有明确收益。这个取舍被记录在
`web/src/types.ts` 顶部。

## 11. 实施记录

### 新增的后端能力

首页的「接着上次」需要跨整棵树找最近修改的文件。按行遍历目录在真实规模下不可行，只列根目录
又是在说谎，所以补了一个能力：

- `store.RecentReader`（可选接口，与 `MarkersFor` 同一模式）：`RecentFiles(ctx, owner, limit)`
- PG 实现用一条递归 CTE 同时取出节点与祖先链，再把路径聚合出来；深度上限 64 防止父链损坏时打转
- 内存实现按 `ModifiedAt` 排序，并显式处理并列，否则首页每次刷新都可能换顺序
- `GET /api/files/recent?limit=`，未实现该能力的后端返回空列表而非报错——首页显示空状态，这是诚实的
- `share.create` 的审计元数据补上 `path`：没有它，日志只能说「share.create 18711bd6」，
  一条无法追溯的记录等于没有记录

### 三个在实施中才暴露的缺陷

**SQL 里的 `id` 有歧义。** recent 的第一版把 `recent` 与 `nodes` 都放进 FROM，两边的 `id`
让 Postgres 直接报 `column reference "id" is ambiguous`。内存后端的测试全绿——因为它测不到
SQL。补了 `recent_pg_test.go`（需要 `TEST_DATABASE_URL`），覆盖排序、嵌套路径、回收站排除、
按 owner 隔离与 limit。教训不是"多写测试"，而是**模拟实现无法验证查询**。

**移动端整列消失。** 手机端靠 `.col:not(.active)` 只显示最深层那一列。我在清理一个未使用的
变量时把携带 `active` 类的计算一并删了，于是所有列都被隐藏，界面上只剩工具栏。这个回归在
1440px 的截图里完全看不出来，是 390px 那一张暴露的——响应式必须真的在窄视口截图。

**CSP 又一次禁用了内联样式。** React 的 `style` 属性写入的是 `style` 特性，同样被
`style-src 'self'` 拦下。上一轮已经踩过一次，这轮换框架后它再次成为陷阱：进度条宽度、
骨架屏宽度、若干对齐全部静默失效。处理方式保持一致——不改 CSP，改代码：

- 动态宽度的进度条换成原生 `<progress>`（`value` 驱动渲染）
- 骨架屏与列宽改为 CSS 选择器
- 项目内约定：**不使用 `style` 属性**，这条写在了 `styles.css` 与 `ui.tsx` 的注释里

### 与上一版的结构对照

| | 0005（Atlas） | 本轮（Atrium） |

| 导航 | 左侧栏 + 标签页 | 顶栏分区，无侧边栏 |
