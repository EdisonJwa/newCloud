# 0007 — S3 存储后端

状态：已实现
相关：`0003-storage-layout.md`（存储布局的两条轴）

## 问题

`storage.backend: s3` 从最初就在配置里，但没有任何实现：启动时直接报错。这比"半可用"好，但
仍然是产品承诺与能力之间的缺口——而缺口写在配置示例里，会被当成已支持。

## 决定

在 `internal/blob/s3` 实现 `blob.Store`（`Put` / `Open` / `Delete` / `Stat`），接到现有的
`blobstore` 之上。**没有**新增第二条写入路径：Web UI、WebDAV、分享、版本、审计仍然共用同一个
内容服务，S3 只是把"字节放在哪里"换掉。

两条轴保持不变：

| 轴 | 取值 | S3 下的行为 |
|---|---|---|
| `backend` | local / s3 | 换掉字节的存放位置 |
| `layout` | blob / tree | `tree` 与 S3 组合被拒绝：它按定义是文件系统镜像 |

## 为什么用 minio-go 而不是 aws-sdk-go-v2

两者都能连 AWS。选 minio-go 的理由是这个产品的用户主要在自建：MinIO、Ceph、R2、B2、Wasabi。
minio-go 就是为这类端点写的——显式 endpoint、path-style 寻址、没有 region 解析的意外，依赖树也
小得多。它也是 rclone 使用的客户端。方向里要求"优先成熟库而不是自己实现协议"，这两个都是成熟
库，差别只在贴合度。

## 三个具体决定

**先哈希再上传。** `Put` 会把字节完整读一遍计算 SHA-256，校验通过后才上传。代价是暂存文件多读
一次；换来的是接口承诺的性质：哈希不匹配的数据**永远不会**进入 bucket。反过来做（先上传再校验
失败后删除）会在出问题的那一刻正好把坏对象留在原地，而那时通常已经没人盯着了。

**`Open` 直接复用 minio-go 的 `Object`。** 它本身实现了 `io.ReadSeeker`，`Seek` 会被转换成
Range 请求——正好是 `http.ServeContent` 需要的。自己写一个基于 Range 的可 seek reader 等于重写
库里唯一已经写对的东西。

**TLS 默认开启。** `secure` 是 `*bool`，零值（未设置）按 `true` 处理。明文传输对象数据必须是
显式选择，而不是从零值继承来的默认。这一点有测试守着：接线测试里忘了设 `secure: false`，
请求立刻打到 `https://` 上失败。

**bucket 必须事先存在。** 建桶需要账户级权限，一个存储服务不该有；桶名写错时应该在启动时
失败，而不是悄悄建出第二个桶。

## 验证

| 层次 | 手段 |
|---|---|
| 客户端契约 | `internal/blob/s3/s3_test.go`：往返、seek（含反向）、哈希不匹配拒绝且不落盘、幂等、尺寸不匹配、删除与不存在的语义、17 MiB 分片上传 |
| 内容层可互换 | `TestS3Conformance`：把**同一套** `layouttest` 一致性套件（17 个子测试：覆盖、版本、删除、列表、跨 owner 拒绝等）跑在 S3 后端上 |
| 接线 | `cmd/newcloud`：`openStorage` 真的构造出 blob 模式的 store 并接受字节；`tree`+`s3` 与未知后端被拒绝 |
| 配置 | endpoint 必填、key 必须成对出现、示例配置能通过校验 |

S3 相关测试在 `TEST_S3_ENDPOINT` 未设置时跳过，所以 `go test ./...` 在没有对象存储的机器上
仍然可用；CI 起一个 moto 的 S3 服务器并把环境变量指过去。

## 边界：没有被证明的部分

**没有对真实 AWS S3 或 MinIO 做过互操作测试。** 验证用的是 moto（一个实现 S3 API 的模拟器）。
它能证明客户端的请求形状、分片、range、错误码处理是对的，但证明不了以下几点：

- 真实服务端的最终一致性行为
- 大文件分片上传在真实网络抖动下的重试
- R2 / B2 / Wasabi 对 `UserMetadata` 与 path-style 的细微差异
- bucket 策略、生命周期规则、服务端加密与这个客户端共存

这些需要一次针对真实后端的验收。在此之前，README 与本文档都按"已实现、仅在模拟器上验证"表述，
不写成"已支持 AWS S3"。

## 未做

- 服务端加密（SSE-S3 / SSE-KMS）：应当由 bucket 策略承担，客户端强行加一层会与服务端加密冲突
- 分片上传的断点续传：当前一次 Put 要么完整成功要么不留可见对象，够用；跨请求续传是另一个量级
- 直接对 S3 提供 Range 代理而不经过应用：会绕开鉴权，因此不做
