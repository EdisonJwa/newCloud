**版本：** v0.2（设计讨论稿）  
**研究日期：** 2026-10-21  
**文档性质：** 产品功能清单、能力边界、技术风险、开发优先级及验收规格

> **范围说明：** 本文只讨论产品功能、协议、系统架构、安全、数据可靠性、运维与验收。**不包含 UI/UX、视觉设计、响应式布局、i18n 或 a11y 方案。**

## 0. 执行摘要

NewCloud 已具备清晰的初始定位：**支持 OIDC 单点登录、WebDAV、受控分享、审计，以及本地/S3 存储的开源自托管文件平台**。目前最大的缺口不是新功能数量，而是若干跨模块契约尚未定义。

**发布前最重要的六个补充方向：**

1. **统一授权：** 个人命名空间、平台角色、资源 ACL、外部分享凭据必须形成一套可执行的权限模型；网页、WebDAV、预览、缩略图、版本下载等入口必须共同遵循。
2. **可靠传输与并发：** 可恢复上传、原子提交、ETag/条件写入、WebDAV LOCK、跨入口冲突处理，防止静默覆盖或不完整文件暴露。
3. **身份和凭据生命周期：** OIDC 用户停用、群组变化、会话/App Password 撤销与 IdP 故障策略必须明确。
4. **数据一致性与恢复：** 对象存储和元数据的提交、重试、清理、备份及实际恢复验证必须形成闭环。
5. **分享安全语义：** 邮箱 OTP、投递箱隔离、下载次数计数、链接过期与撤销都需要可测试的定义。
6. **可运维性：** 后台任务、队列、迁移、存储诊断、审计验证、告警、备份恢复缺一不可。

**产品范围建议：** 先把“开放且可靠的文件平台”做好，暂不引入在线 Office、IM、AI 助手、复杂工作流引擎或自研桌面同步客户端。

### 优先级定义

| 等级 | 定义 |
| --- | --- |
| **P0 / Release blocker** | 关系到安全隔离、数据完整性、协议正确性或基础可运维性；未通过则不可对外宣称 Production Ready。 |
| **P1 / Core product** | 日常使用的重要功能；可以在安全的技术预览版中部分延期，但应在完整 1.0 中实现。 |
| **P2 / Differentiation** | 形成长期竞争力的增强能力，建立在 P0/P1 之上。 |
| **P3 / Research** | 需要额外论证成本、安全边界和维护义务的长期方向。 |

以下不变量比页面或 API 的数量更重要。

| ID | 不变量 | 发布验收 |
| --- | --- | --- |
| INV-01 | 每次文件读写、搜索、预览、历史访问及分享访问均执行统一对象级授权 | 任一入口均不能绕过资源/用户边界 |
| INV-02 | 所有写入遵循统一版本、条件请求与锁规则 | 网页和 WebDAV 并发修改不出现静默覆盖 |

| INV-06 | 后台任务幂等、可重试并可识别遗留产物 | 进程中断后可重新收敛 |
| INV-07 | 版本历史、回收站、配额和物理 GC 共用可验证的引用/保留规则 | 恢复、清理和去重不导致误删 |

| INV-09 | 审计覆盖授权决策和敏感操作，并允许独立验证完整性 | 缺日志、乱序、篡改和日志系统故障可检测 |

授权应采用“默认拒绝、每次请求校验”的策略。[S7]

## 3. 身份、会话与应用凭据

### 3.1 OIDC 基线（P0）

| 需求 ID | 功能要求 | 优先级 |
| --- | --- | --- |
| ID-01 | 使用 **`(iss, sub)`** 作为外部身份唯一键，内部再映射不可变 `user_id`；不得以邮箱作为主键 | P0 |
| ID-02 | Authorization Code Flow；适用时使用 PKCE；校验 issuer、audience、签名、有效期、state、nonce | P0 |
| ID-03 | OIDC Discovery、JWKS 密钥轮换和验证失败策略 | P0 |
| ID-04 | 首次登录 JIT 创建用户，提供允许/拒绝自动开户的管理策略 | P0 |
| ID-05 | IdP `groups` 映射平台角色；未知组/缺失 Claim 不得自动获得高权限 | P0 |
| ID-06 | 用户停用、群组移除、权限降低后，现有 Session 和 App Password 的撤销/降权策略 | P0 |
| ID-07 | IdP 离线时的登录、新建会话、已有会话续期和撤销行为有明确规则 | P0 |
| ID-08 | 账号删除/禁用后，文件归属、共享、审计和保留数据有确定策略 | P0 |
| ID-09 | 可选 SCIM 或管理 API 自动化开户/停用及群组同步 | P2 |

OIDC Core 指明 `(iss, sub)` 才是可依赖的稳定身份组合；Pocket ID 的 `groups` Claim 需要请求相应 Scope。[S1][S2] Pocket ID 在刷新 Token 时会检查用户是否禁用或被移出允许组，但 **NewCloud 自签发的 Session/App Password 不会因此自动撤销**，必须另行落实。[S2]

### 3.2 应用密码（P0）

- 每个凭据具有独立 ID、名称、创建时间、可选过期时间、最后使用时间和可撤销状态。
- 使用密码学安全随机数生成高熵秘密；服务器仅保存适当的验证材料，日志中不得记录明文。
- 明确定义 **只读、读写、WebDAV、自动化** 等作用域，而不是所有 App Password 默认拥有账户全部权限。
- 应用密码不得授权执行系统管理、创建更高权限凭据等敏感操作（除非有明确单独授予的受限能力）。
- 支持单个撤销、全部撤销以及账户停用后的批量撤销；需要验证并发请求中的撤销窗口。
- 所有凭据只能通过 HTTPS 使用；注意 WebDAV 客户端通常使用 HTTP Basic 携带应用凭据，禁止通过非 TLS 传输。
- 设置速率限制、失败审计及暴力猜测防护。

### 3.3 Break-glass 本地管理员（P0）

- 与外部 IdP 独立，允许在 IdP 不可用时完成必要的恢复操作。
- 与普通管理员区分；默认仅具有系统恢复和配置权限，**不隐式赋予所有用户私有文件的读取权限**。
- 强认证、凭据离线保管、使用后告警、强制审计、定期恢复演练。
- 对此入口的公开网络暴露、访问范围、口令重置和锁定策略制定独立决策。

**验收示例：** 同一邮箱被 IdP 重新分配给新用户时不能继承原用户文件；移除管理员组后不再拥有管理权；注销后服务端会话实际失效。[S1][S8]

## 4. 多用户隔离与资源授权

### 4.1 推荐的三层权限模型（P0）

1. **Platform Role：** 决定账户管理、系统配置、审计读取等平台动作；不直接意味着读取个人文件。
2. **Resource ACL：** 决定对特定文件、目录或空间的操作权，可由所有者、直接授权、组授权或继承产生。
3. **Share Capability：** 链接或收件人 OTP 赋予的受限、可到期、可撤销的外部访问能力。

建议内部权限原语至少区分：`list`、`read`、`download`、`create`、`overwrite`、`rename`、`move`、`delete`、`share`、`manage_permissions`、`view_history`。预设角色可以更简单，但必须能映射到这些原语。

### 4.2 最重要的授权规则

- `COPY`：同时验证源读取权限、目标创建权限、冲突和配额。
- `MOVE`：验证源移动/删除权限及目标创建权限；继承的 ACL 和分享状态如何变化必须事先确定。
- 目录递归操作：不能只检查根目录，忽略内部受特殊保护的文件。
- 版本恢复：恢复历史版本是一次新写入，应验证当前写入权，并保留历史。
- 文件删除/永久清理：区分普通删除、恢复、永久删除和管理员保留策略。
- 权限继承：父目录 ACL 变化是否影响已授予的子项权限要有确定规则。
- 授权查询不能依赖用户可以篡改的文件路径或前端传来的角色字段。
- 任何跨用户/空间缓存和索引必须保留授权边界；搜索命中不泄露无权访问的文件存在性。

### 4.3 配额定义（P0）

明确区分：

- **逻辑配额：** 用户可见文件当前版本总大小。
- **保留用量：** 历史版本、回收站、未完成上传及共享空间的计费归属。
- **物理容量：** 去重、压缩和存储副本之后的实际占用。

**建议：** 先以容易解释的逻辑配额为用户配额基础，额外对未完成上传和保留版本设置服务端资源上限；不要把跨用户内容去重带来的物理空间节省直接混为用户授权或容量配额。

## 5. 文件服务与 WebDAV

### 5.1 文件核心操作（P0）

- 目录创建、重命名、复制、移动、删除及恢复；文件上传、读取、覆盖及下载。
- 支持带明确覆盖规则的同名冲突处理；不进行不经确认的静默覆盖。
- 唯一文件 ID 与稳定版本 ID；路径改名和移动后的标识保持一致。
- 大型目录使用分页/游标与稳定排序，避免一次列出全部对象。
- 递归操作有幂等处理、错误汇总、取消规则和可追踪的任务 ID。
- 路径校验覆盖 `..`、编码/解码差异、符号链接、大小写冲突、Unicode 规范化及各客户端非法名称。

### 5.2 WebDAV 方法与协议契约（P0）

| 范畴 | 需求 |
| --- | --- |
| Discovery | `OPTIONS`、允许的方法、DAV 级别与能力声明准确 |
| Metadata | `PROPFIND`、`PROPPATCH`、`207 Multi-Status`、live/dead properties |
| Files | `GET`、`HEAD`、`PUT`、`DELETE`、`MKCOL`、`COPY`、`MOVE` |
| Locks | `LOCK`、`UNLOCK`、锁令牌、超时/刷新、Depth 以及锁冲突 |
| Conditions | `ETag`、`If-Match`、`If-None-Match`、WebDAV `If`、正确的 `412/423` 等状态码 |
| Partial reads | HTTP `Range`、`If-Range`、`206/416`，特别是媒体与断点下载 |
| Recursive semantics | `Depth`、覆盖目标、目录递归及权限检查 |
| Compatibility | Windows、macOS、Linux、rclone、Cyberduck 等客户端的行为回归 |
| Optional extension | RFC 6578 Collection Synchronization，作为增量同步能力研究项 |

RFC 4918 是核心规范；RFC 9110 定义 HTTP 条件请求和 Range；RFC 6578 定义 WebDAV Collection Sync 扩展。[S3][S4][S5]

### 5.3 统一并发规则（P0）

- 网页/API 和 WebDAV 必须进入相同的写入仲裁层。
- 条件写入失败时显式返回冲突，而不是“最后一次写入覆盖前一次”且不通知客户端。
- Lock 的语义需适用于跨接口操作；只有服务器内部可理解的锁不算完整兼容。
- 发生服务重启、锁超时、MOVE/COPY、版本恢复和共享访问时，锁状态不出现自相矛盾。
- 版本历史不是放任并发覆盖的替代品。

### 5.4 WebDAV 与同步客户端的范围界限

| 能力 | 当前定位 |
| --- | --- |
| 远程文件访问/挂载 | WebDAV 的核心目标 |
| 可恢复上传 | 独立上传协议/能力，不由 RFC 4918 自动提供 |
| 文件夹本地自动同步 | 独立客户端及同步状态机，非 v1 必需 |
| 冲突副本、选择性同步、离线变更 | 未来客户端项目需另行规范 |
| Collection Sync 增量报告 | 可作为未来同步能力的基础之一，不能替代完整客户端 |

## 6. 上传、下载与派生文件处理

### 6.1 可靠上传（P0）

建议提供独立于 WebDAV `PUT` 的可恢复上传通道；优先评估 **tus 1.0** 或等价、经过充分测试的协议。[S6]

必须有：

- 创建上传会话；绑定目标父目录、授权主体和预期目标。
- 分块/偏移校验、上传会话过期、重试幂等、暂停/恢复所需的服务器状态。
- 大小、速率、并发数及临时资源配额限制；保护公共投递箱不耗尽磁盘。
- 收尾阶段校验内容完整性，再原子地暴露最终文件版本。
- 如果目标已被修改，提交阶段重新验证 ACL、ETag、配额、链接有效性及目标冲突。
- 中断的未完成上传可清理；服务重启后能恢复或安全取消。
- 直接上传 S3 与经服务端代理上传的最终文件语义一致。

### 6.2 下载与共享次数（P0）

- 普通下载支持 Range、条件响应和大文件流式传输。
- 分享链接的“最大下载次数”不能简单地按 HTTP 请求数计费，因为一次媒体播放或断点续传可能产生多个 Range 请求。
- **建议定义 `authorized_download_session`：** 下载次数按成功核准的逻辑下载会话原子扣减，并设置会话 TTL、文件版本绑定和重放防护。具体口径需 Owner 决策。
- 直接发放 S3 预签名 URL 时，无法自然提供严格的“一次下载即失效”语义；AWS S3 文档明确说明同一预签名 URL 在有效期内可以重复使用。[S11]
- 对于必须严格撤销或计数的分享，默认经应用网关验证每次请求，或设计等效的存储侧一次性授权方案。

### 6.3 安全预览与缩略图（P0）

当前已规划：图片、音视频、PDF、文本与源码预览；PNG/JPEG/GIF 缩略图；SVG/HTML 永不内联。建议保留这些保守默认值，并补充：

- 缩略图、转码结果和缓存视为原文件派生的受保护资源，不得使用公开、可猜测的永久 URL 绕过授权。
- 解码/解析器使用隔离进程、超时、内存和像素/帧数预算；限制压缩炸弹、恶意媒体和元数据解析。
- 不信任客户端 MIME 或扩展名；对允许内联展示的格式严格检测并限制内容处理方式。
- 处理队列可重试，失败结果有冷却和回收策略；避免持续重试恶意文件耗尽资源。
- 缩略图和索引缓存的访问、失效与 GC 绑定原文件权限、版本及删除状态。
- 可选恶意软件扫描与文件隔离；对匿名投递建议至少提供扫描/隔离钩子以及严格资源上限。

这些控制与 OWASP 文件上传安全建议一致。[S9]

## 7. 分享与协作

### 7.1 已规划的外部分享（保留）

- 随机不可预测的分享链接。
- 密码保护、绝对过期时间、下载次数上限。
- 指定邮箱收件人的一次性验证码核验。
- 临时“投递箱”上传链接。

### 7.2 必须补齐的共享语义（P0/P1）

| 需求 ID | 要求 | 级别 |
| --- | --- | --- |
| SHARE-01 | 链接拥有独立 ID、权限、失效状态与版本/资源引用，默认最小权限 | P0 |
| SHARE-02 | 密码/OTP 验证有速率限制、有效期、尝试上限及重放防护 | P0 |
| SHARE-03 | OTP 与预期邮箱绑定，避免将“知道链接”视为收件人身份 | P0 |
| SHARE-04 | 投递箱 Upload Only：不可列目录、读文件或查看其他上传者内容 | P0 |
| SHARE-05 | 分享上传需要文件数、单文件大小、总空间、速率和保留期限限制 | P0 |
| SHARE-06 | 链接吊销与文件删除/移动/权限变化的影响明确，覆盖缓存和衍生资源 | P0 |
| SHARE-07 | 下载次数扣减具备事务一致性并考虑并发 Range 请求 | P0 |
| SHARE-08 | 账户间、群组间直接共享文件或文件夹，支持权限继承 | P1 |
| SHARE-09 | 共享资源的转授权、转移和管理权规则明确 | P1 |
| SHARE-10 | 集中列出已创建/收到的分享及其真实有效授权 | P1 |
| SHARE-11 | 团队拥有独立归属权的共享 Space，不依赖个人账号存续 | P2 |

**需明确的安全政策：** 分享链接是否允许访问历史版本？是否跟随移动？目标目录权限收回后是否保持链接有效？匿名投递的数据归谁、如何计入配额、何时删除？

## 8. 文件版本、回收站与生命周期

### 8.1 必要要求（P0）

- 每个版本具有不可混淆的 ID、创建时间、内容校验信息及操作者引用。
- 恢复旧版本会创建新版本，原有历史不被覆盖。
- 明确文件删除后如何处理版本、共享和缩略图；回收站中的数据是否占用配额。
- 支持对回收站的恢复、永久删除和保留期清理；防止未授权恢复到无权限的目录。
- 定义管理员强制保留与用户“永久删除”之间的优先级。
- 版本、回收站、分享和正在进行的下载可能共同引用同一 Blob，物理 GC 必须确保没有有效引用。
- 对清理任务提供审计与可重复执行语义。

### 8.2 建议明确的配置参数

| 参数 | 说明 |
| --- | --- |
| `version_retention_days` | 旧版本最长保留期，需明确管理员覆盖规则 |
| `version_count_limit` | 单文件版本数或容量上限 |
| `trash_retention_days` | 回收站默认保留期 |
| `upload_session_ttl` | 未完成上传会话的过期时间 |
| `share_max_ttl` | 分享链接最大允许有效期 |
| `public_upload_max_total_bytes` | 单个投递箱可接受的总上传量 |

**注意：** 上表是建议配置项，不是已确定的默认值；推荐通过数据保留策略评审后再给具体数字。

## 9. 存储抽象、数据一致性与安全

### 9.1 推荐的逻辑分层

```text
Identity / Session / Credential
             |
        Authorization
             |
     File Service API
             |
   Namespace + Metadata -------------- Audit Event / Outbox
             |
     Version / Lock / Quota
             |
    Transfer / Blob Lifecycle
             |
       Storage Adapter
          /      \
       Local     S3-compatible
          \      /
        Layout Adapter
        /          \
      Blob        Tree
```

这是一张**职责图**，不是强制微服务拓扑；MVP 完全可以是一个模块化单体进程。

### 9.2 Blob / Tree 的共同契约（P0）

- 对外统一逻辑文件 ID、版本 ID、Etag 和命名空间语义。
- `blob` 的内容寻址应对引用计数、跨版本保留、事务中断及 GC 进行完整处理。
- 如允许跨用户物理去重，需要评估存在性侧信道、配额误导和跨账号数据生命周期；**MVP 建议以单信任域的去重为限**。
- `tree` 必须明确是否允许管理员在文件系统外部直接修改目录。若允许，则必须设计重新扫描、冲突侦测与元数据修复；若不允许，应显式写入运维限制。
- 防止符号链接逃逸、路径穿越、目录竞态及大小写不兼容行为。
- 两种布局可以有不同的性能/容量特征，但不得在文件授权或数据完整性上提供不同保证。

### 9.3 数据写入状态机（P0）

建议：

```text
INITIATED -> RECEIVING -> VERIFIED -> STORED -> COMMITTED -> AVAILABLE
                  |          |         |          |
                  +----------+---------+----------+--> FAILED / CLEANUP
```

- 文件对象持久化确认和元数据事务不能简单视为同一原子事务；设计幂等恢复与协调机制。
- 元数据提交后事件写入推荐使用事务 Outbox 或等效可靠投递，避免“写成功但审计/索引事件丢失”。
- 对象已持久化但元数据提交失败时，保留临时对象并按 TTL/引用信息安全清理。
- 严格区分对象存在、元数据可见及用户有权限读取三件事。
- AWS S3 具有强 read-after-write 一致性，但**不意味着 S3 与应用数据库之间天然存在分布式事务**；S3 兼容服务也需逐一验证。[S12]
- 清理未完成 Multipart Upload；AWS 明确建议对残留分块设置生命周期规则，否则可能持续产生费用。[S13]

### 9.4 加密与密钥管理（P0/P1）

- TLS 必需，反向代理转发协议与可信源列表必须有显式配置。
- 本地磁盘及 S3 的服务端静态加密作为可配置存储安全策略；密钥不应与无保护的数据备份存放在同一故障域。
- 应定义密钥轮换、加密状态验证及密钥丢失后的恢复边界。
- **不在 v1 宣称端到端加密（E2EE）**，因为服务器预览、去重和全文索引与端到端保密性存在明显架构冲突，需另行研究。

### 9.5 数据导入/导出与迁移（P1/P2）

- 能导出用户拥有的文件与必要元数据，不依赖独有数据库才能读取原始内容。
- 规划数据库 Schema 迁移、版本回滚和兼容检查。
- 存储后端或布局迁移需具备校验、暂停/恢复与切换前回滚方案；MVP 不要求在线热迁移。

## 10. 审计与安全事件

### 10.1 事件范围（P0）

至少包含：认证成功/失败、会话创建/撤销、App Password 创建/使用/撤销、文件下载/上传/修改/删除/恢复、共享创建/使用/修改/撤销、ACL 变化、角色变化、管理配置变更、恢复操作、审计校验失败。

推荐字段：`event_id`、`occurred_at`、`actor_id`、`auth_method`、`source`、`action`、`target_id`、`target_version_id`、`result`、`reason_code`、`request_id`、`prev_hash`、`event_hash`。仅在必要时存储 IP/设备信息并制定保留策略；不在审计中记录密码、OTP、完整 Token 或完整分享链接。

### 10.2 哈希链及验证（P0）

- 使用标准化序列化和确定性事件排序，确保同一事件数据生成同一摘要。
- 明确并发写入时的顺序控制；检测事件缺号、链断裂和非法重排。
- 定期导出或签署审计检查点，保存于**独立于主数据库管理员权限**的信任域。
- 提供 `audit verify` 独立校验命令，并验证导出的 CSV/JSON 与原始记录的对应关系。
- INSERT-only 数据库角色可以减少应用层误删，但不能阻止拥有更高数据库/系统权限的攻击者重写链条。
- 可选 WORM 存储；AWS S3 Object Lock 提供这种存储模型，但不能假设所有 S3 兼容实现具有等价保证。[S10]

### 10.3 审计故障模式（P0）

必须有明确策略：当日志数据库满、链写入失败、外部检查点不可达或事件积压时，哪些高风险操作应失败关闭，哪些只需本地持久缓冲和告警。不可对用户显示成功，但同时丢失被承诺必需的审计事件。

OWASP 推荐记录应用安全事件，并验证日志注入、资源耗尽、写入失败及权限保护等故障情形。[S14]

## 11. 可靠运维、部署与灾难恢复

### 11.1 P0 运维能力

| 模块 | 必须具备的功能 |
| --- | --- |
| 配置 | 版本化配置、启动前校验、机密配置与普通配置分离 |
| 健康探测 | Liveness、Readiness；存储、数据库、队列等依赖诊断 |
| 后台任务 | 任务 ID、幂等、失败重试、死信/隔离、超时、取消和恢复 |
| 备份 | 文件对象、元数据、身份映射、配置及密钥的协调备份 |
| 恢复 | 新实例真实恢复、权限和版本一致性验证、RPO/RTO 目标定义 |
| 数据完整性 | 校验和扫描、缺失对象/孤儿对象检测、修复报告 |
| 可观测性 | 请求错误率、DAV 冲突率、上传失败率、队列积压、GC 与审计校验指标 |
| 部署 | TLS/反向代理设置、可信头、存储目录权限、最小进程权限 |
| 数据库 | Migration、备份一致性、升级前检查、失败回滚 |
| 资源预算 | 最大文件、并发上传、预览转换、搜索/缩略图后台负载限制 |

### 11.2 恢复验证不等于“有备份文件”

恢复演练至少包括：

1. 从一个全新环境重建程序配置和数据库。
2. 恢复对象/文件数据及加密密钥（如启用）。
3. 验证文件权限、版本、回收站、群组映射与审计链。
4. 验证备份时间点附近的并发写入不会产生丢失引用。
5. 记录可证明的恢复时长、恢复点和剩余错误。

CISA 建议使用离线/加密备份并定期测试可用性与完整性。[S15]

### 11.3 不应提前承诺的能力

- 在没有跨节点锁、会话、任务协调与一致性验证前，不宣称 Active-Active 或高可用多节点写入。
- 在没有完成异常测试前，不宣称任意 S3 兼容存储完全等价。
- 在没有稳定变更日志与冲突状态机前，不宣称“类似 Dropbox 的双向同步”。

### 12.2 P1 — 完整核心产品

## 13. 建议的实施顺序与阶段 Gate

| Gate | 研究与实现范围 | 进入下一阶段的要求 |
| --- | --- | --- |
| G0 — 规则冻结 | 文件 ID、版本、ACL、群组、配额、共享、并发、保留和错误契约 | 关键设计决策签署，冲突情景有确定结果 |
| G1 — 统一文件内核 | Namespace、Metadata、Local Blob、版本、条件写入、引用和 GC | 基础文件操作/多用户隔离/崩溃恢复通过 |
| G2 — 身份和 WebDAV | OIDC、App Password、Lock、PROPFIND/PROPPATCH、HTTP 条件请求 | 跨入口冲突、真实 DAV 客户端互操作通过 |
| G3 — S3 和可靠传输 | S3 Adapter、可恢复上传、提交协调、任务恢复 | 断网、进程中断、S3 错误注入无数据破坏 |
| G4 — 共享和审计 | OTP、投递箱、下载次数、凭据撤销、哈希链及校验 | 权限撤销、滥用测试、审计可验证 |
| G5 — 运维和发布 | 备份恢复、升级、指标、安装部署、完整安全回归 | 发布验收矩阵满足，才允许 Production Ready |

## 14. 必须建立的验收与故障注入矩阵

| 测试 ID | 场景 | 预期结果 |
| --- | --- | --- |
| T-01 | 用户 A 猜到用户 B 的文件 ID、版本 ID、缩略图或下载链接 | 无权获取内容或私有元数据 |
| T-02 | 管理员组移除后沿用旧 Session 和 App Password | 在设计的撤销窗口内权限降低/访问失效 |
| T-03 | 网页与 DAV 同时覆盖一个文件 | 统一条件写入规则生效，绝不静默覆盖 |
| T-04 | 上传 80% 时断网，再继续 | 不重复已确认的分块，完成后校验正确 |
| T-05 | 存储写入完成但元数据提交失败 | 不出现可见半成品；临时对象最终可清理 |
| T-06 | 元数据提交和事件写入之间进程崩溃 | 重试后审计/任务事件不丢、不重复计费 |
| T-07 | 文件恢复、回收站和历史版本共享同一 Blob | GC 不删除仍被引用的内容 |
| T-08 | 带下载次数上限的共享遭到并发 Range 请求 | 计数原子、无法超额绕过或错误耗尽 |
| T-09 | 邮箱 OTP 暴力尝试/重放/跨链接复用 | 达到阈值被拒绝；OTP 与收件人和分享绑定 |
| T-10 | 投递箱上传者试图读目录/读取他人的文件 | 只能执行被授权的上传操作 |
| T-11 | 分享撤销后利用缩略图、缓存和预签名 URL | 满足明确的撤销时效；禁止未承诺的旁路 |
| T-12 | 利用路径穿越、符号链接及大小写/Unicode 名称冲突 | 不离开授权命名空间，不覆盖意外目标 |
| T-13 | S3 多段上传未完成且进程异常退出 | 会话可修复或安全回收，不无限消耗资源 |
| T-14 | 解码损坏媒体、超大尺寸图片、压缩炸弹 | 资源预算有效，进程隔离且服务保持可用 |
| T-15 | 审计表被删除/改写/插入非法事件 | 校验报告可检测链或外部检查点不一致 |
| T-16 | 审计存储不可用或磁盘写满 | 遵循事先约定的 fail-open/fail-closed 策略 |
| T-17 | 从异地全新环境恢复数据库、文件和密钥 | 恢复权限/历史/数据完整性；记录实际 RPO/RTO |
| T-18 | Mac Finder、Windows DAV、Linux 挂载、rclone、Cyberduck | 测试范围内各客户端完成读取/写入/锁/移动回归 |
| T-19 | 大目录分页过程中持续新增、删除和重命名 | 无越权、重复/遗漏行为符合游标一致性契约 |
| T-20 | `COPY/MOVE` 目标存储满、权限变化或链接过期 | 操作不会破坏源文件，失败可以诊断与恢复 |

**注意：** 表中 `80%` 只是故障注入位置，不是上传恢复性能承诺；RPO/RTO、撤销窗口、并发容量等数值应通过实际场景和测量后确定。

## 15. 尚待产品 Owner 决策（不要由 Agent 擅自假设）

| 决策 ID | 待决定问题 | 建议默认方向 |
| --- | --- | --- |
| D-01 | 管理员能否读取个人私有文件？ | 默认不能；如需紧急访问，设计受控授权和审计 |
| D-02 | Group Claim 消失/IdP 不可用时现有权限如何处理？ | 禁止权限升级；定义有限缓存与撤销期限 |
| D-03 | App Password 的能力范围及默认有效期？ | 独立范围、可撤销、最小权限 |
| D-04 | 外部分享的下载次数如何计数？ | 原子授权下载会话，不按 Range 请求数 |
| D-05 | 投递箱文件归属及配额规则？ | 计入目的目录所有者/空间；独立临时限制 |
| D-06 | 版本、回收站、未完成上传的容量如何计费？ | 逻辑用户配额加服务端保留上限 |
| D-07 | Tree 能否接受应用外文件系统修改？ | MVP 默认禁止；另行研究可侦测模式 |
| D-08 | Blob 是否跨用户去重？ | MVP 默认不跨独立安全域去重 |
| D-09 | 生产初期支持单节点还是多节点？ | 先单节点，暂不承诺 Active-Active |
| D-10 | 哪些审计故障强制阻断业务？ | 按操作风险分级并强制文档化 |
| D-11 | 系统数据保留与永久删除政策？ | 区分用户请求、管理员保留与备份周期 |
| D-12 | S3 兼容性的认证清单及能力下限？ | 声明具体验证后端，不声称无限兼容 |
| D-13 | 本地/S3、Blob/Tree 是否同版全部生产可用？ | 按真实测试矩阵单独授予支持状态 |
| D-14 | 是否必须在 v1 实现直接用户/群组共享？ | 如定位团队云盘则应提升为 P0；否则 P1 |
| D-15 | 是否提供公开文件 API 和长效自动化凭据？ | 优先只支持必要 DAV 和受限 App Password |

这些是**需要明确选择**的问题，不是要求每项立即复杂化。Owner 可以保留“未决”，但相应能力不可因此默认为 Production Ready。

## 16. 暂不纳入当前主线的功能

以下项目没有被否定，但会显著扩大数据模型、安全攻击面或长期维护负担：

- 在线 Office、多人实时协作、IM 和视频会议。
- 无明确威胁模型的 AI 文件助手或第三方云端文档解析。
- 全量端到端加密（需要与服务器预览、搜索、分享、去重重新权衡）。
- 自建插件商城、任意第三方插件执行环境。
- 复杂工作流引擎与多租户 SaaS 计费平台。
- 未经验证的多地域双活写入和强一致跨集群文件系统。

## 18. 最终建议

NewCloud 不缺一个更长的功能清单。真正需要冻结的是**跨入口授权、并发控制、可恢复上传、分享限制、存储状态、回收/保留、审计完整性和灾难恢复**这八个契约。

**推荐原则：**

1. 先稳定单节点、清晰模块边界与可测试的数据语义，再考虑分布式部署。
2. 优先复用成熟规范（OIDC、RFC 4918、HTTP 条件请求、tus），避免自行创造协议。
3. 功能声明与测试证据一一对应；规划、开发完成、集成通过、生产批准为不同状态。
4. 不为了支持所有可能的云盘扩展而牺牲普通文件操作的正确性。
5. 发布门槛以安全、数据完整性、恢复和跨客户端回归为准，而不是演示成功。

**建议的产品定位：** 一个开放、安全、可靠、可独立部署的文件与分享平台；待基础能力成熟后，再逐步发展团队空间、丰富检索和同步生态。
